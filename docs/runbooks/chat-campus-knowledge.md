# SmartMap campus prompt and knowledge maintenance

The instructions for how Chat responds are in `lib/ai/prompts/campus-assistant.ts`. The admin AI Knowledge screen edits searchable campus facts, not the system instructions. Its records arrive as untrusted data. Never store secrets, personal records, private prompts, or scraped page markup in an active knowledge entry.

## Rollout and rollback

- `supabase/seed_ai_knowledge_vsu.sql` fills **missing titles** in a controlled initial seed. It does not overwrite existing rows; the normal Supabase reset only uses its configured `seed.sql`. Do not run the historical delete/reinsert seed against an existing database.
- For an existing **approved** environment, preview `supabase/patch_ai_knowledge_vsu_20261127.sql`. It rolls back by default. It only matches unique titles that retain the exact stock content, source, keywords and priority. It preserves UUIDs, keywords, priority and active state. It skips missing, duplicate, already-corrected rows or rows with edits to the guarded stock fields. An inactive flag is preserved. A skip is not permission to overwrite.
- Record the intended rows by UUID, previous and replacement content/source, and revision before applying. Quiesce concurrent editorial edits and rehearse on a disposable database. In the approved transaction, compare the returned UUIDs to the approved preview and roll back on any difference. Only an authorized operator should commit the reviewed transaction on the intended database and verify those UUIDs afterward.
- Prefer the authorized admin editor for an intentional review of a skipped row. Direct SQL does not call the app’s knowledge cache revalidation; coordinate refresh of the retrieval tag and verify eventual readback (the retrieval cache can live for about one hour). Confirm intended database row readback first, then refresh retrieval and verify it with a query that misses the answer cache. Only after retrieval reflects the new facts, deploy the reviewed prompt version to open a fresh answer-cache namespace. A database-only edit does not invalidate stored answers; do not broadly delete cached records to force a refresh. For an already-live database-only correction or rollback, the max-profile retrieval refresh may serve stale content on the first read. Verify the new data on an answer-cache miss; then use a fresh reviewed answer namespace or wait for affected answers to expire. In staging, check a previously warmed exact question and a never-queried question. A code or SQL test is not live validation.
- Roll back by UUID and only if current fields still match what was changed. Restore the captured previous content/source, preserve unrelated editor changes, refresh the knowledge cache, and deploy a verified new release if reverting the prompt itself.

Smoke cases: unknown room code returns no made-up pin; a Tolosa question does not silently route to Baybay; library “open now” does not assert live hours; “Where do I open a quiz or virtual class?” points to VSUEE, while personalized grades go to my.VSU without asking for an ID; and student schedules preserve only supported room and event details.

## Rehearse the operator SQL offline

Use Node 22 and two trusted, clean local checkouts. The first checkout must contain the pre-refresh seed; for this change use commit `18cc334e48c490f009f58de7f6b92b611df360de`. The second checkout contains the candidate, including the script below. Install the pinned fixture dependency from your trusted npm registry into a temporary directory:

```sh
fixture="$(mktemp -d)"
npm install --prefix "$fixture" --no-audit --no-fund --ignore-scripts @electric-sql/pglite@0.6.0
node tools/qa/rehearse-knowledge-refresh.mjs /path/to/pre-refresh-checkout "$PWD" "$fixture"
```

Run this from the candidate checkout. Both tests use in-memory databases with synthetic editorial edits. The second test commits only in memory and checks default rollback, guarded application, preservation of skipped rows and a no-op second application. This does not exercise hosted PostgreSQL, RLS, concurrent operators, or live data. The standard database CI job does not run this script.

## Gemini default and configured fallbacks

The code fallback order is `gemini-3.5-flash-lite` then `gemini-3.1-flash-lite`. A supported explicit `GEMINI_MODEL_IDS` list preserves its order, so changing the checked-in example does not change a deployment setting. Use exact supported model IDs; set any higher-cost Flash model explicitly. `gemini-2.5-flash-lite` remains opt-in for existing providers that still have access, not the default. The older `gemini-2.5-flash` alias is normalized to `gemini-3.5-flash-lite` rather than depending on Google's December 1 redirect. The old `gemini-3.5-flash` alias is not automatically upgraded to higher-priced Flash.

Use [Google's model deprecation notice](https://aistudio.google.com/docs/deprecations), [sampling guidance](https://aistudio.google.com/docs/whats-new-gemini-3.6#sampling-parameter-deprecation), and [current pricing](https://ai.google.dev/gemini-api/docs/pricing) when changing settings. The adapter uses provider-default sampling and structured JSON. On the published standard paid text rates reviewed November 27, 2026, the new 3.5 Flash-Lite primary is $0.30 input and $2.50 output per million tokens, versus $0.25 and $1.50 for 3.1 Flash-Lite. It is not a savings over the former primary. Review actual tier and expected volume before rolling out any paid traffic. Keep model changes separate from quota purchases or deployment settings. Before any public Gemini rollout, verify the intended audience and handling of user-provided data against [Google’s Gemini API terms](https://aistudio.google.com/docs/terms). The terms restrict clients likely to be accessed by under-18s and say not to send sensitive, confidential, or personal information to unpaid services. A paid tier does not itself resolve the age restriction. Do not enable public use merely because staging tests pass. For exact approved nonproduction smoke, verify requested and returned model IDs, structured output, and bounded calls; do not record credentials, user text or raw provider responses.

For an approved offline fallback, `CHAT_LLM_ENABLED=false` sends ordinary JSON and streaming Chat requests to static campus help before answer-cache lookup. It is not a provider-wide off switch: the secret-gated Chat health route can still send a synthetic request directly. If zero provider traffic is required, the authorized operator must account for that route and any external callers, and verify no provider requests in the approved environment. Do not flip live settings or call the live probe as a substitute for this check.
